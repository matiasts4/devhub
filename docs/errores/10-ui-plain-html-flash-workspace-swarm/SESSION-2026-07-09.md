# Sesión 2026-07-09 — Thrash / FOUC / TypeErrors terminales

**Objetivo de la sesión:** estabilizar la UI de terminales/workspace tras el strip de optims de carga (`fix/strip-terminal-load-optim`), entender por qué el usuario veía “crasheos” sin señal en la terminal del server, y aplicar un fix **sistémico** (no solo un parche).

**Resultado al cierre:** menos errores percibidos; TypeError y FOUC Times New Roman bajo control; quedan longtasks/jank residuales (sobre todo pizarra).

**Branch:** `fix/strip-terminal-load-optim`  
**HEAD al inicio (aprox.):** `696efbe2` y vecinos (ctx bag helpers).  
**Al cierre:** cambios **locales sin commit** (ver § Archivos modificados).

---

## 1. Contexto previo (de qué veníamos)

- Se hizo strip de optims agresivas de cold-load (ver `strip-load-optim.md`).
- Baseline deseada: comportamiento estable tipo pre-optim, sin perder producto (WebView2, decompose, pizarra).
- Tras el strip parcial: **imports/helpers incompletos** y bag de `viewportCtxRef` inconsistente.
- Commits recientes de la rama tocaban pasar helpers al ctx bag (`1bfd47c2`, `696efbe2`) para que el churn recovery no explotara — insuficiente si el hook **sombrea** imports con `const { refreshTerminalViewport } = c`.

## 2. Problema de diagnóstico (malentendido clave)

### Lo que decía el usuario

- “Crasheo” al cambiar workspace, salir de pizarra, series de cambios rápidos.
- A veces no veía **nada** en la terminal del server.
- Síntoma visual: CSS se va milisegundos, sidebar se aplasta, iconos al fondo, HTML plano; a menudo **se auto-arregla**.

### Lo que se miraba al principio (incorrecto solo)

- Solo `crash.log` / TypeError.
- Si no había TypeError nuevo → “no hay crash”.

### Aclaración (acordada en sesión)

Hay **tres clases** de fallo que el usuario llama igual “crasheo”:

| Clase | Evidencia | Ejemplo en sesión |
|-------|-----------|-------------------|
| **A. TypeError** | `data/logs/crash.log` | `refreshTerminalViewport is not a function` (~18:38Z y antes) |
| **B. Longtask / tormenta layout** | `browser.log` `visual-thrash` + `longtask` | 500–800ms → luego ~100–250ms |
| **C. FOUC CSS** | `browser.log` Times New Roman, `css-var-missing` | Geist → Times; `--surface-app` vacío |

**Pipeline de errores de cliente:**

```
Browser window.onerror / probe
  → POST /api/client-log
  → data/logs/browser.log
  → (crash/error) data/logs/crash.log + dumps
```

Si el write de client-log va bien, **antes no había `console.error` en Next** → la terminal del server “no decía nada”. Se añadió echo `[devhub][client-crash]` en `crashLog.js`.

## 3. Timeline de la sesión (resumen)

### Fase 1 — TypeError `refreshTerminalViewport is not a function`

- **Stack:** `useTerminalLayoutChurnRecovery` → `handleLayoutSettled` ← `dispatchTerminalLayoutSettled` ← lifecycle de paneles.
- **Causa:** destructuring del ctx bag **sombrea** imports del módulo; bag incompleto → `undefined` no es función.
- **Fix:**
  - No tomar pure helpers del ctx en el churn hook (solo imports de `TerminalTTY.helpers`).
  - `installXtermTeardownSafety` al boot del engine y en layout-settled.
  - `safeTerminalRepaint` centralizado.
  - Echo de crashes al stdout del server (`crashLog.js`).

### Fase 2 — “No veo nada en el server” + crasheos sin TypeError

- Usuario insiste: crasheo visual sin rastro formal.
- **Instrumentación:** `visualThrashProbe.js` montado desde `useClientErrorLogger`.
  - Escribe `source: visual-thrash` en `browser.log`.
  - `probe-started` = prueba de vida (si no aparece, el bundle no cargó el probe → hard refresh).
- Primeras capturas reales:
  - `css-var-missing` `--surface-app` (tenía `#080808`)
  - `shell-flex-lost`: Geist → **Times New Roman**, flex → block
  - Tormenta de `hot-window` reason **`pizarra-mode-exit`** en cada switch de workspace
  - Longtasks 100–185ms (y picos peores)

### Fase 3 — Root cause tormenta pizarra

```js
// useWorkspacePanelLifecycle — BUG
useEffect(() => {
  notifyNativeLayoutSettled(pizarra ? 'enter' : 'exit');
}, [notifyNativeLayoutSettled, pizarraOwnsLiveSurfaces]);
// notifyNativeLayoutSettled se recrea con activeWsId/windows →
// re-dispara pizarra-mode-exit en CADA switch sin flip real de pizarra
```

**Fix:**

- Solo disparar cuando `pizarraOwnsLiveSurfaces` **cambia de verdad**.
- Ref para notify; no cold-start `pizarra-mode-exit` si pizarra ya está off.
- `SharedTerminalSurface`: host workspace **no** se etiqueta `pizarra-mode-exit` → `shared-surface-host-activate-workspace`.

### Fase 4 — FOUC (Times New Roman)

- Confirmado: stylesheets caen (ej. 9→8, 8→7) en dev (HMR / style tags de Next/Turbopack).
- **FOUC shield:**
  - Inline `#devhub-fouc-shield` en `src/app/layout.js`
  - Estático `public/fouc-shield.css` (fuera del grafo webpack)
  - Tokens mínimos, flex en shell/sidebar, fondo `#080808`, fuentes sans
- App sidebar: quitado `opacity: 0` en enter/exit (solo slide X) — FOUC de chrome.

  - Tras `handleFitAllView`: dispatch en `requestAnimationFrame` (no mismo longtask).

## 8. Decisiones de diseño a no revertir

1. **Pure helpers nunca desde ctx bag** (solo imports de módulo).
2. **Effects de pizarra solo en cambio real de ownership**, no en identity de callbacks.
3. **Soft vs hard** en el bus: soft = un repaint; hard = burst/reattach.
4. **Soft path no llama** `syncTerminalViewportOnWorkspaceShow`.
5. **FOUC shield** vive fuera del CSS graph de webpack (inline + `/fouc-shield.css`).
6. **Diagnóstico:** thrash visual se mide con `visual-thrash`, no solo con crash.log.

### Follow-up 2026-07-09 ~22:05 local — cráter idle = pizarra-blank-recovery

**Usuario confirma:** en el evento que vimos en logs (longtask + `pizarra-blank-recovery` ~02:03Z) vio **solo iconos**, fondo OK, estética desordenada, recuperación rápida, **mientras no hacía nada** (idle).

**Cadena causal:**

1. `WorkspaceRightDock` timer 420ms (`pizarra-blank-recovery`) si cree que pizarra está en blanco.
2. Hacía `dispatchTerminalLayoutSettled({ reason: 'pizarra-blank-recovery', panelIds: [] })`.
3. Bug de contrato: **`panelIds: []` se interpretaba como “todos los terminales”** (solo se filtraba si `length > 0`).
4. Todos los `TerminalTTY` corrían soft recovery + reflow del host (`minHeight` thrash) → ResizeObserver + longtasks 200–300ms.
5. Paint intermedio: utilidades CSS “flojas” → cráter estético (iconos, layout) con fondo del shield intacto.

**Fix:**

- Blank recovery **ya no** despacha layout-settled a terminales; solo evento dock-local + resize suave.
- Cooldown 8s por workspace; umbral de blank más estricto.
- Churn: `panelIds.length === 0` → **ningún** terminal reacciona.
- Severity `pizarra-blank-recovery` = **noise** en el bus.
- Probe: kind nuevo **`aesthetic-crater`** (icono se infla y/o labels desaparecen).

### Follow-up 2026-07-09 — E9 terminal negra + E10 click-blocker navegador invisible

**Síntomas (usuario, screenshot + descripción):**

1. **E9 — Terminal pegada / negra con cursor:** a veces carga, a veces no; se ve la barrita/cursor parpadeando; zona del panel negra. Longtasks residuales “creciendo”.
2. **E10 — Clicks del header de terminal van al navegador:** no puede usar expandir/maximizar/cerrar del panel; “parece que están los botones del navegador superpuestos pero no se ven”; al apretar “desplegar” se abre ventana del browser del workspace **aunque el navegador no esté abierto**.

**Causa E10 (confirmada en código):**

```js
// useWorkspaceRightDockSync — BUG
const browserLive =
  dock?.visible && (dock?.activeTab === 'browser' || dock?.maximizedView === 'browser');
```

- `maximizedView` por defecto es `'browser'` y **queda stale** cuando el tab activo es editor/swarm/pizarra.
- El rAF del dock llamaba `setNativeBrowserVisibility({ visible: true })` aunque el usuario no estuviera en el tab browser.
- WebView2 es HWND nativo: **no respeta** `pointer-events: none` / opacity del React dock → robaba hits sobre el chrome de las terminales (botones focus/close).
- Cerrar vía `dock-not-browser` pelea con ese re-show.

**Fix E10:**

- Helper puro `isNativeBrowserDockLive(dock)` en `rightDockState.js`:
  - `visible === true` **y**
  - `activeTab === 'browser'` **y**
  - si maximizado, `maximizedView === 'browser'`.
- Mismo predicado en rAF live sync + efecto `dock-not-browser` (`useRightDockController`).
- Tests de regresión en `rightDockState.test.js`.

**Causa E9 (parcial, alineada con docs/06 RC0):**

- Soft path de layout recovery solo hacía `safeTerminalRepaint`.
- Con dims que ya coinciden + addon GPU null/context-lost, `canSkipLayoutSettledRepaint` podía **saltar** recovery → terminal negra con cursor (xterm vivo, paint muerto).
- Soft no re-adjuntaba GPU.

**Fix E9:**

- `canSkip` falla si `needsGpuRendererReattach` o WebGL context lost.
- Soft severity: si hace falta GPU → `scheduleBoundedGpuRecover(16)` (backbone acotado, **no** multi-burst / full show-sync).
- Soft sigue siendo un solo repaint cuando el GPU está bien.

**Cómo verificar:**

1. Hard refresh / restart Tauri.
2. Abrir browser del dock un momento, cambiar a otro tab o cerrar dock → clicks en maximize/close de terminal deben responder, **sin** abrir ventana browser.
3. Switch de workspace/ventana: terminales no deben quedarse negras con cursor parpadeante; si lo hacen, revisar browser.log por `soft-escalate-gpu-recover`.
